## 4. 新增后台运行状态

仅在实验 ON 条件编译内增加：

```c
static bool s_rf_background_active;
static rf_dispatch_cmd_t s_rf_background_command;
```

用途：

- 标记当前是否存在已提交或已发送的后台命令；
- 保存后台命令 id、source、policy generation、QUERY/SET、目标模式和目标功率；
- 在队列消费和 REPORT 返回时再次核对身份；
- 在节点消失、设备 announce、用户新命令抢占或后台命令关闭时清理。

该状态只存在于 RAM，不新增 Flash 写入。

## 5. 后台命令生命周期

### 5.1 周期评估

周期入口在实验 ON 下按顺序执行：

1. `rf_power_reconcile_pending_intent()`：协调用户命令；
2. `rf_power_background_controller_periodic()`：评估后台命令。

后台评估期间：

1. 获取 RF 状态锁；
2. 从网关 raw RF 状态填充 mapper input；
3. 映射为 CQ runtime state；
4. 调用 runtime adapter 得到下一状态和可能的后台命令；
5. 对 IDLE、POLICY_ALREADY_APPLIED、STALE、READY_QUERY、READY_SET 等结果应用下一状态；
6. 若有命令，复制到局部变量后释放 RF 锁；
7. 在锁外调用 `rf_cq_submit()`。

RF 锁内没有调用 MQTT、NVS、ZBOSS send 或阻塞式队列操作。

### 5.2 提交失败回滚

如果 `rf_cq_submit()` 失败：

1. 重新获取 RF 锁；
2. 重新映射当前运行态；
3. 调用 CQ-3e rollback；
4. 只有当命令 source 为 PERIODIC、id/generation 仍匹配、没有用户意图、waiting/submitting 或 dispatch active 时，才清除本次后台 ownership。

回滚不会清除 `policy_apply_pending`，因此节点仍会在后续评估周期继续收敛。

### 5.3 消费者发送

消费者收到命令后按 source 分流：

- 用户命令：沿用原有用户意图路径；
- `RF_CQ_SOURCE_PERIODIC`：进入后台发送路径。

后台发送前调用 `rf_background_dispatch_plan_create()`，再次判断：

- 活动命令 id/generation；
- TTL 是否过期；
- 是否出现用户意图；
- 是否已有 REPORT waiting/submitting；
- 是否有 dispatch active；
- 节点短地址是否有效；
- 下一个低层私有帧序号。

状态含义：

- SEND：可发送；
- CLOSE_EXPIRED：TTL 已过，关闭后台 ownership；
- CLOSE_STATE_CHANGED：已被用户或其他状态抢占，关闭后台 ownership；
- CLOSE_INACTIVE：节点地址无效，关闭后台 ownership；
- DROP_STALE：旧命令，不修改任何当前状态；
- INVALID_ARG：非法命令，不发送。

### 5.4 REPORT 最小关闭

匹配的后台 REPORT 返回后，本阶段只做最小 ownership 关闭，避免下一轮评估一直看到 `background_command_active=true` 而拒绝新评估。

这不是完整 CQ-3f 集成：以下内容仍在 CQ-4c/4d 处理：

- 后台 QUERY 的 `report_received` 发布策略；
- 后台 SET 满足目标时的 `confirmed`；
- MQTT 负向通知节流；
- 命令表动作描述；
- timeout 和 send failure 完整策略。

## 6. 代际与抢占

`rf_power_policy_init()` 现在会在实验 ON 下保证初始策略代际有效：

```text
0 或 UINT32_MAX -> 1
```

原因：0 表示未初始化，不能作为后台命令的有效 generation；UINT32_MAX 是用户命令的 GENERATION_ANY，也不能作为后台具体策略版本。

用户发起新的 MANUAL/AUTO 命令时，会在同一 RF 锁内：

1. 清理旧 waiting；
2. 清理旧后台 ownership；
3. bump policy generation；
4. 安装新的用户意图。

因此旧后台 REPORT 或旧队列命令不能确认新用户事务。

## 11. CQ-4c：后台 REPORT 完成策略

### 11.1 阶段结论

CQ-4c 已把 CQ-3f 的 REPORT 完成策略正式接入实验 ON 的 `rf_power_aps_indication_cb()`：

- 后台 QUERY 的匹配 REPORT 发布 `report_received`；
- 后台 SET 的匹配 REPORT 在满足目标时发布 `confirmed`；
- mismatch REPORT 不关闭活动事务；
- 后台状态消息不使用用户 `request_id`；
- 默认 OFF 路径继续保持原逻辑。

实验开关仍未默认启用，实验 ON 固件仍不得视为产品化运行。

### 11.2 普通匹配 REPORT

在 waiting 分支中，低序号 REPORT 仍必须同时满足：

1. v2 数据包；
2. `report_seq == expected_seq`；
3. 若有期望功率，报告功率必须一致；
4. 若有期望模式，报告模式必须一致。

匹配后：

- QUERY：通过状态计划器发布 `report_received`，关闭后台 ownership；
- SET：通过状态计划器发布 `confirmed`，关闭后台 ownership，并清除 `policy_apply_pending`；
- 用户命令仍按原有 `request_id` 路径返回，不与后台命令混用。

### 11.3 节点自发高序号 REPORT

第一轮独立复审发现：后台 SET 已发送、waiting 尚未结束时，节点如果主动发送高序号 REPORT，旧逻辑会先进入 waiting 的严格匹配分支并判定 MISMATCH，导致即使节点已经满足目标，也无法及时确认。

修复后的窄分支仅在以下条件全部满足时接受：

1. `RF_COMMAND_QUEUE_ENABLED=ON`；
2. `report_seq >= 0x80`；
3. `rf_power_report_is_new_unsolicited_locked(report_seq)` 判定为新报告；
4. 当前不是用户事务（`!expected_user`）；
5. 存在活动后台命令，且 policy generation 匹配；
6. 活动后台命令是 SET；
7. `policy_apply_pending=true`；
8. 报告 mode/power 已满足该 SET 的目标。

满足后由 `rf_background_status_plan` 发布 `confirmed`、清理 background 和 policy pending，随后调用 `rf_power_clear_waiting_locked()` 同步结束 waiting。

以下情况不会确认或改变活动事务：

- 旧高序号报告：`RF_REJECT_OLD`；
- 新高序号但不满足活动后台 SET 目标：`RF_REJECT_MISMATCH`；
- 活动后台 QUERY 的高序号报告：不接管；
- 用户事务等待期间的高序号报告：不放宽；
- v1 报告：不能满足 SET 完成条件。

### 11.4 MQTT 发布边界

MQTT 发布仍在 RF 临界区外执行。RF 临界区内只进行：

- 活动命令快照；
- 纯策略判断；
- background ownership、policy pending 和 waiting 的 RAM 状态更新。

后台 QUERY/SET 的 MQTT 消息强制：

```text
request_id = NULL
```

因此后台命令不能冒用用户 `request_id`，后端用户等待者不会被后台消息误完成。

## 12. CQ-4d：后台 timeout / send failure 终态策略

### 12.1 阶段结论

CQ-4d 已把 CQ-3f 的两个负向终态正式接入实验 ON 路径：

- waiting 满 90 秒：`WAIT_TIMEOUT`；
- `esp_zb_aps_data_request()` 非 OK：`SEND_FAILED`；
- SET 负向终态后继续保持 `policy_apply_pending=true`；
- QUERY 负向终态不改变已有 `policy_apply_pending`；
- timeout/failed MQTT 负向通知按 5 分钟节流；
- 即使通知被节流，活动命令仍会内部关闭。

默认 OFF 路径仍保持原逻辑，实验 ON 仍未产品化启用。

### 12.2 新增 RAM 状态

仅在实验 ON 条件编译内新增：

```c
static uint32_t s_rf_last_negative_notice_ms;
static bool s_rf_terminal_notice_pending;
static uint16_t s_rf_terminal_notice_addr;
static rf_background_publish_status_t s_rf_terminal_notice_status;
```

用途：

- `s_rf_last_negative_notice_ms`：记录上一条已发布 timeout/failed，用于 5 分钟负向节流；
- 其余三个变量：在通用 waiting 过期函数于 RF 锁内关闭后台命令后，暂存终态通知，等退出 RF 临界区后发布。

这些状态只在 RAM，不新增 Flash 写入，不新增任务。

### 12.3 Timeout 路径

后台控制器每次评估前先检查：

1. `s_rf_report_waiting=true`；
2. `s_rf_wait_started_ms != 0`；
3. `now - wait_started_ms >= RF_POWER_SETTLE_MS`（90 秒）；
4. 当前不是用户事务；
5. background policy generation 与当前策略一致。

满足后调用 CQ-3f `WAIT_TIMEOUT`：

- SET：关闭 background/waiting，并设置 `policy_apply_pending=true`；
- QUERY：关闭 background/waiting，不改变已有 pending；
- 若 5 分钟内已有负向通知，则内部关闭、不发布；
- 若允许发布，则更新负向通知时间戳并发布 `timeout`。

### 12.4 Send failure 路径

后台命令实际调用 `rf_power_execute_plan()` 后，如果 `err != ESP_OK`，且活动命令 id、generation 与当前策略仍匹配：

1. 调用 CQ-3f `SEND_FAILED`；
2. SET：保持/设置 `policy_apply_pending=true`；
3. QUERY：不改变已有 pending；
4. 清理 background 和 waiting；
5. 根据负向节流决定是否发布 `failed`。

`rf_tx_note_result_locked()` 仍继续维护既有的发送失败计数与退避窗口。

### 12.5 旧 generation 与迟到报告防护

复审等待期间额外收紧了两个防护：

1. timeout closure 中，如果 `s_rf_background_command.policy_generation != s_rf_policy_generation`，只内部清理 background/waiting，不调用 `WAIT_TIMEOUT`，也不发布；
2. send failure 后置身份判断要求 active background 的 policy generation 等于当前策略 generation，否则不发布、不修改。

timeout 后 waiting 和 background 都已清理；迟到低序号 REPORT 会进入 OLD，不能再次确认。

### 13.3 状态与保存边界

状态流为：

```text
waiting → testing → test_passed/test_failed → committed/error
```

- testing 满 5 分钟未完成：转 `test_failed`，错误码 `TEST_EXPIRED`；已经通过的子步骤保持 `passed`，仍 pending 的子步骤标为 failed；
- test_passed 满 5 分钟：回 waiting 并清空快照；
- failed 不能准备提交；
- committed/error 下重复准备提交返回 `INVALID_STATE`；
- test_id 必须由集成层生成且在一次配网会话内唯一，不得复用；
- 组件不是线程安全的：HTTP 接入时必须单任务调用或外层加锁。

### 14.3 路由和请求映射

适配器支持：

```text
GET  /api/provision/status
POST /api/provision/test
POST /api/provision/commit
POST /api/provision/cancel
```

能力包括：

- 未知路径返回 404；
- 路径存在但方法不匹配返回 405；
- JSON 请求体最大 4096 字节，超限返回 413；
- 有 JSON body 时要求 `Content-Type: application/json`，不匹配返回 415；
- JSON 语法错误、对象类型错误或字段缺失返回 400；
- 已有活动测试返回 409；
- `/test` 超过 60 秒 5 次返回 429；
- 未注册 commit handler 返回 501。

错误响应只包含错误码与字段名，不回显用户输入，也不返回 Wi‑Fi/MQTT 密码。

### 14.4 全请求限流

初版只在会话内核中限流，413、415、坏 JSON 等请求在进入会话前就返回，理论上可被恶意重复发送。现已调整：

1. `handle_test()` 在任何协议级处理前调用 `iot_prov_note_test_rate_limit()`；
2. 限流通过后再检查 body、Content-Type 和 JSON；
3. 最终通过 `iot_prov_begin_after_rate_limit_ex()` 启动，避免同一请求被重复计数；
4. 新增 `test_invalid_test_requests_rate_limited`，覆盖坏 JSON、错误 Content-Type、413、空 body、字段错误后第 6 次请求返回 429。

### 14.5 敏感数据生命周期

请求体会复制到适配器的 `parse_scratch` 供 cJSON 解析。现在：

- 新请求开始前先清空 scratch；
- cJSON 对象释放后立即清零 scratch；
- cJSON 解析失败返回 NULL 时也立即清零 scratch；
- `handle_test()` 栈上 `session_request` 在返回前清零；
- `handle_commit()` 栈上 `bundle` 在各成功/失败返回路径清零。

会话内核中的快照仍是业务状态，按取消、失败、过期或提交生命周期清理。

### 14.6 commit handler 契约

当前 commit handler 是同步调用，设计文档已明确：

- handler 必须快速、有界，不能长时间占用 HTTP server worker；
- 只有完整 bundle 已持久化并收到底层成功确认，才可返回 `IOT_PROV_OK`；
- handler 执行时间必须明显短于测试 5 分钟 TTL；
- 真实接入时需要写入超时和失败恢复路径；
- 如果后续无法保证快速完成，应设计异步保存状态，而不是简单改用新 tick。
