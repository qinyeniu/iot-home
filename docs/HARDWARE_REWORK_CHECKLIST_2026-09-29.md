# 2026-09-29 网关 OLED 硬件整改与受控复测清单

- 状态：**待用户在硬件旁实施**
- 前置结论：默认 OFF 8 小时长测为 FAIL/WARN，其中 I2C/OLED 为独立硬件/接线高概率问题
- 重要限制：整改完成并经用户确认前，不启动新长测、不打开串口、不刷固件、不改配置

## 1. 长测中需要通过硬件整改验证的问题

2026-09-28 默认 OFF 8 小时长测中，网关侧观察到：

```text
clear bus error: 29 次
OLED refresh failed: 6 次
```

所有异常均通过现有本地恢复机制恢复，未造成长期业务中断，也没有证据表明是 panic、内存不足或意外重启。现象更符合 OLED 模块、杜邦线/面包板接触、上拉不足或供电去耦不足。

本次整改的目标不是增加固件逻辑，而是先排除物理层和供电问题。

## 2. 所需物料

| 物料 | 数量 | 用途 |
| --- | ---: | --- |
| 4.7 kΩ 电阻 | 2 个 | SDA、SCL 分别上拉到 3.3 V |
| 100 nF 陶瓷电容 | 1 个 | OLED VCC 就近去耦 |
| 可靠 USB 数据线 | 1 条 | Zigbee 节点全程使用，测试中不更换 |
| 短而固定的 SDA/SCL 连接线 | 1 组 | 降低接触电阻和干扰 |
| 万用表 | 1 个 | 检查短路、上拉电平、供电 |
| 扎带/胶带/固定件 | 若干 | 固定 OLED 排线和 USB 接口，避免中途松动 |

> 若当前 OLED 模块自带上拉，仍可临时外加 4.7 kΩ；ESP32-C6 内部上拉阻值较大，不建议把内部上拉作为长 I2C 排线的唯一上拉。

## 3. 网关 OLED/I2C 整改步骤

### 3.1 断电和拍照

1. 在用户方便操作硬件时进行，整改前断开网关 USB 供电；
2. 对现有接线拍照，记录 SDA、SCL、VCC、GND 当前位置；
3. 不改变 Zigbee NVRAM、Flash、分区表，不做任何刷写操作。

### 3.2 缩短并固定 SDA/SCL

1. 将 OLED 的 SDA、SCL 杜邦线尽量缩短，避免松散飞线；
2. SDA、SCL 避免与 Wi‑Fi/Zigbee 天线、USB 电源线长距离并行；
3. 插紧面包板或端子连接处，必要时更换氧化/松动的杜邦线；
4. 用扎带或胶带固定排线，使拉扯 USB 线时不会带动 SDA/SCL；
5. 保持网关与 OLED 共地。

### 3.3 增加 4.7 kΩ 上拉

1. SDA 通过一个 4.7 kΩ 电阻上拉到 3.3 V；
2. SCL 通过一个 4.7 kΩ 电阻上拉到 3.3 V；
3. 电阻尽量靠近 OLED 或总线主控端，避免悬空长线；
4. 不要把 SDA/SCL 上拉到 5 V。

### 3.4 增加 VCC 去耦

1. 将 100 nF 陶瓷电容就近接在 OLED 模块 VCC 与 GND 之间；
2. 电容引脚尽量短；
3. 注意极性：普通 100 nF 陶瓷电容通常无极性，不要误装电解电容。

### 3.5 上电前检查

1. 用万用表通断/电阻档确认：
   - VCC 与 GND 不短路；
   - SDA 与 GND 不短路；
   - SCL 与 GND 不短路；
   - SDA 与 SCL 不短路；
2. 确认电阻连接方向为 SDA/SCL 到 3.3 V，而不是到 GND；
3. 确认 100 nF 电容跨接在 VCC/GND 之间；
4. 确认 OLED 地址与当前固件一致，不更换不同地址的屏幕。

### 3.6 上电后的只读/短测前确认

后续需要在用户同意后才能打开串口。打开前先做物理确认：

1. OLED 有供电表现或背光/屏幕状态符合当前模块；
2. 排线轻按时不应黑屏或重启；
3. 设备管理器中仍应能看到 COM5、COM6；
4. 记录整改后的接线照片和电阻/电容实际位置。

## 4. Zigbee 节点 USB 数据线整改

1. 节点全程使用一条已确认能稳定供电和传输的 USB 数据线；
2. 8 小时复测期间不更换数据线、不重新插拔；
3. USB 接口与线缆应固定，避免意外拉扯；
4. 若条件允许，节点和网关不要通过供电能力不足的扩展坞串接。

虽然上一轮日志没有证据证明数据线导致复位或采集中断，但供电/RF 裕度不能仅靠日志完全排除，受控复测必须先消除该变量。

## 5. Windows 热点与外网稳定性准备

受控 8 小时复测前需确认：

1. Windows 热点持续开启，电脑不会睡眠、关机或自动重启；
2. 2.4 GHz 热点信道和周边环境保持稳定；
3. 外网和 MQTT Broker 在测试开始前持续可达；
4. 网卡电源管理不应在夜间关闭设备；
5. 测试期间不手动切换网络、不停止热点、不重启电脑；
6. 记录测试开始时网关获得的 IP 地址和 Broker 地址。

若热点或外网无法保证稳定，应推迟复测，避免再次把外部网络故障混入固件结论。

## 6. 建议复测顺序

### 6.1 第一步：10–30 分钟受控短测

在用户确认硬件整改完成后，再单独征得用户同意：

1. 打开 COM5、COM6 采集日志（可能触发一次复位）；
2. 观察启动、Zigbee 入网、MQTT connected、OLED 刷新；
3. 重点确认是否还出现 `clear bus error` 或 `OLED refresh failed`；
4. 轻触/轻拉固定后的排线，确认不会导致屏幕或总线异常；
5. 短测结束后先分析日志，再决定是否进入 8 小时长测。

### 6.2 第二步：受控 8 小时长测

短测无阻断性问题，并且用户明确同意后再启动：

- 测试期间不更换节点 USB 数据线；
- 不停止 Windows 热点；
- 不刷写、不改配置；
- 网关 COM6、节点 COM5 双侧持续采集；
- 保留完整原始日志和自动/人工分析结果。

## 7. 受控复测通过口径（建议）

### 7.1 I2C/OLED

理想结果：

```text
clear bus error = 0
OLED refresh failed = 0
OLED 持续刷新
```

若仍出现 1 次以上 `clear bus error`，即使自动恢复，也应继续按 WARN/FAIL 复核，并区分：

1. 接线仍松动；
2. OLED 模块本身异常；
3. 上拉阻值或安装位置不合适；
4. 供电噪声仍存在；
5. 硬件整改后仍需评估 I2C 速率或固件恢复统计。

### 7.2 Zigbee 父链路

理想结果：

```text
Rejoin failure = 0
正式 link lost = 0
parent unavailable 不持续累积
节点 REPORT_SEND 与网关 RF sample 连续
```

若外网稳定且 I2C 已整改，但仍复现首次异常早于网络故障、Rejoin failure 聚集、长时间父链路中断，再进入 ZBOSS polling/rejoin、child aging、coexistence 和供电方向的只读分析，不先叠加新功能。

### 7.3 Wi‑Fi/MQTT 与资源

建议同时确认：

1. Wi‑Fi 不出现 beacon timeout；
2. MQTT 无长时间断连；
3. 不出现 write completion stall；
4. 无 panic、watchdog、brownout、`ESP_ERR_NO_MEM`、assert failed 或意外重启；
5. free heap / minimum heap / largest block 不持续下降。

## 8. 未完成确认前的工作边界

在用户明确说明“硬件整改已完成”前：

- 不启动 10–30 分钟短测；
- 不启动 8 小时长测；
- 不打开 COM5/COM6；
- 不重新编译或覆盖当前固件；
- 不继续 P2 Zigbee 应用事件队列拆分；
- 不擦 Flash、不擦 Zigbee NVRAM、不刷 bootloader/分区表。
