## 12. analyze_serial_log.py 离线代码审查（未修改工具）

审查文件：`tools/analyze_serial_log.py`（当前工作区最终版，约 16,986 字节）。

### 12.1 已确认优点

- 逐行读取，未一次性载入文件；command/RF tail 使用固定长度 deque；
- 当前版本已移除全量 no-buffer point 列表，只保留 sliding window 与达阈值 burst；
- 输入使用 UTF-8 + `errors="replace"`，输出显式重配置为 UTF-8，可适配 Windows CRLF；
- `json.loads` 仅解析数据，不使用 eval；
- AST 核验导入仅为标准库。

### 12.2 阻塞结论

在真实 478,241,805 字节日志 `firmware/gateway/log.overnight-gw-20260923-034906.txt` 上实测：共 5,978,215 行，ANSI 彩色 no-buffer 行以 `ESC[0;31mE (...) ZB_ESP_MAC...` 开头。当前 `LOG_LINE_RE` 锚定 `I/W/E` 开头，无法解析这些行的 uptime 和日志级别；结果显示 `mac_no_buffer=5,960,289`，但 `max_events_in_60s=1`、显著突发 0，并给出无危险信号提示，核心结论失真。修复方向：解析前移除标准 ANSI CSI 序列，并基于 stripped line 解析级别、uptime、tag 与 message。

另建议将 MAC no-buffer 事件限定为 `ZB_ESP_MAC` tag 下的 `No buffer`，而不是任意行包含该短语，避免 MQTT/业务日志造成误计。

### 12.3 后续非阻塞加固

- MQTT 正则在极长畸形行上呈 O(n²)；建议前缀判断后按 ` = ` 分割并直接校验 JSON 首尾；
- 捕获 `RecursionError`（深嵌套 JSON）并校验顶层为对象、`command` 为字符串；
- uptime 回跳时重置 sliding window/current burst，并分段计算 uptime 覆盖；
- 校验 `--max-examples` 非负且设置合理上限；对非字符串/超长 MQTT command 归类；
- 对文件不存在/权限错误给出简洁 CLI 错误和非零退出；补充少量回归样本（ANSI、多段重启、畸形 JSON）。

## 16. 2026-09-24：`iot_product_config_save_bundle()` 尝试、复审与撤回

### 16.1 范围

- 实验修改：`firmware/common/iot_product_config/iot_product_config.c`

- 构建仍显示 Zigbee 1.6.0、应用分区剩余约 5%，仅作为风险记录。

### 16.2 复审结论：Block

新增接口的参数校验、写锁获取、单一 NVS handle、失败路径资源 close/give 基本正确，但“全部 set 成功后一次 `nvs_commit()`”不能保证多键原子性。

ESP-IDF v5.5.4 中，`nvs_set_str()` 经 `NVSHandleSimple::set_string()` 直接调用 `Storage::writeItem()`；`Page::writeEntry()` 立即写 flash，而 `NVSHandleSimple::commit()` 对普通 NVS handle 仅校验后返回 `ESP_OK`。因此，若 Wi-Fi ssid/pass 或部分 MQTT 键已写入，后续某个 `nvs_set_str()` 返回空间/硬件错误，函数即使不调用 `nvs_commit()`，前面的键也可能已经持久化，形成半套配置。

目标代码位置：`firmware/common/iot_product_config/iot_product_config.c:428-447`。

### 16.3 后续最小修复方向

- 不要把一次 `nvs_commit()` 当作多键事务；
- 可选方案 A：将完整配置序列化为单个 NVS blob，blob 数据先写、索引后写，并让加载路径只接受完整 bundle blob；
- 可选方案 B：写入 staging 键和事务 generation/state，完整后再通过 durable marker 切换，并在启动恢复中清理未完成 staging；
- 若只需覆盖普通 API 失败而不覆盖掉电，可先快照旧键并在失败时回滚，但仍不能满足此前契约中的掉电恢复要求。

撤回后已重新执行网关构建并通过。构建版本号为 `a22d902`，仍使用 Zigbee 1.6.0；应用分区仍剩约 5%。构建期间出现的 `zb_have_full_active_sample` 未使用函数警告为现有代码警告，本次没有顺手修改，避免混入无关改动。

## 18. 2026-09-24：NVS 配置事务与恢复设计文档

### 18.1 新增文件

- `docs/NVS_CONFIG_TRANSACTION_DESIGN.md`

### 18.2 文档结论

1. 当前 Wi‑Fi/MQTT 字段仍按多个独立 NVS 字符串键保存，普通 NVS handle 的一次 `nvs_commit()` 不能提供多键事务或回滚；
2. 完整配置最大约 453 字节，适合序列化为单个 NVS blob，不需要修改分区表；
3. 方案 A 为单一完整 blob，代码较少，但依赖 NVS 单个 item 更新的一致性；
4. 方案 B 为 `cfg_stage` 完整 blob + `cfg_commit` durable marker，掉电和失败边界最清楚，推荐用于产品化 SoftAP `/commit`；
5. 多字符串 staging 因键多、恢复复杂且易出现字段不一致，不推荐；
6. 旧散列键先作为 legacy 回退保留，不在启动时自动迁移；等用户下一次通过 SoftAP 明确保存并测试成功后再写新格式；
7. NVS encryption、Secure Boot、Flash encryption、分区表调整、Zigbee NVRAM 清理均不在本阶段执行。
