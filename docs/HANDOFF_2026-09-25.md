### 3.2 本阶段功能

- 每 60 秒读取 AHT20 温湿度；
- BH1750 使用 one-shot high-resolution 命令 `0x20`；
- 使用与现网节点一致的 raw APSDE-DATA 路径构造标准 ZCL Report Attributes；
- 温度为 `int16`，单位 0.01 °C；
- 湿度为 `uint16`，单位 0.01 %；
- 光照为 `uint16`，按 Zigbee 对数照度编码：`10000 × log10(lux + 1)`，并限制在 `0xFFFD`；
- 本地提交被拒绝时最多重试 3 次；
- 帧已经发出但 APS 未确认时，本阶段不做无线补报，等待下一个采样周期，以减少电量消耗；
- AHT20/BH1750 任一读取失败时，本地 ZCL MeasuredValue 会恢复为 invalid，并清除缓存样本对应 valid flag，避免网关主动 Read 读到陈旧值。

### 11.2 判定规则

- `PASS`：达到目标时长，且未发现失败或降级线索；
- `DEGRADED`：发现节点 `REPORT_STATS` 中 APS/I2C/队列等增量失败，或发现观察缺口；
- `FAIL`：发现 assert/panic/abort、重启标志、uptime 回跳，或 MAC no-buffer 风暴；
- `INCOMPLETE`：默认 8 小时目标时长未满足，且尚未发现降级或失败线索。

判定优先级为 `FAIL > DEGRADED > INCOMPLETE > PASS`。工具逐行读取日志，使用固定长度 sliding window/deque 统计 MAC no-buffer，避免长日志导致内存膨胀。

### 12.3 存储设计

采用独立于 legacy 散列键的三个 NVS 项：

- `cfg_a`：A 槽完整配置 blob；
- `cfg_b`：B 槽完整配置 blob；
- `cfg_commit`：durable marker。

`bundle_payload_t` 固定 455 字节，包含：

- schema version；
- Wi‑Fi SSID/password；
- MQTT URI/username/password/client ID。

`bundle_marker_t` 固定 17 字节，包含：

- magic；
- schema version；
- active slot；
- payload length；
- generation；
- payload CRC32。

保存顺序：

1. 读取当前 marker；没有 marker 时默认写 A 槽；
2. 选择当前 active slot 的另一个槽；
3. 将完整 payload 写入非活动槽并立即 `nvs_commit()`；
4. 数据槽提交成功后，再写 `cfg_commit` marker 并提交；
5. marker 切换前旧配置保持可用；marker 切换失败或中途掉电，加载路径仍指向旧 active slot。

加载时 fail-closed：检查 marker 长度、magic、schema、slot、payload length、数据 blob 长度、CRC32 和字段合法性；任何异常都不会猜测性加载另一个槽。

### 12.4 与 Legacy 的隔离

新键 `cfg_a/cfg_b/cfg_commit` 与旧键：

- `version`
- `wifi_ssid`
- `wifi_pass`
- `mqtt_uri`
- `mqtt_user`
- `mqtt_pass`
- `mqtt_cid`

完全分离。保存 bundle 不会调用 legacy schema 初始化，也不会覆盖或删除旧键。当前只是给后续 SoftAP `/commit` 提供事务型底层能力。

## 13. 电池传感器阶段 3：按需 I2C 控制器

### 13.1 修改范围

### 13.2 本阶段变化

- 启动时不初始化 I2C；
- Zigbee 未入网时不初始化 I2C；
- 如果已有 I2C 但节点离线，会主动释放 I2C；
- Zigbee joined 后，每次采样前临时初始化 I2C；
- 采样并提交三条 APSDE-DATA 请求后，释放 I2C 控制器；
- AHT20 每个采样周期按需初始化；
- BH1750 继续使用 one-shot `0x20`，读数完成后器件自动进入 power-down。

这样可以避免空闲期间保持 I2C 控制器。但该改动**不等于切断传感器电源**，AHT20/BH1750 的 VCC、I2C 上拉和板上其他漏电仍需硬件检查。

### 13.3 离线构建

### 24.1 修改内容

在 `firmware/gateway/main/main.c` 的 `rf_power_policy_persist()` 中，打开既有 `rfpol` namespace 后先读取当前：

- `mode`
- `mpwr`

若两个键都读取成功且与待保存值完全相同，则关闭 NVS 句柄并记录：

```text

```

缺键、读取失败、值不同、NVS 损坏等情况均保守继续写入，避免把异常状态误判为“无需更新”。

### 24.2 目的和边界

该改动用于减少重复点击或重复发送相同 SET/AUTO 时的 `nvs_set_*` + `nvs_commit`，降低 Flash 磨损。它不会阻止 RAM 中保留 `s_rf_policy_apply_pending`，因此 Flash 中策略相同但节点实际状态不一致时，后续仍会校正节点。

首次创建 `rfpol` namespace 时，ESP-IDF 仍可能因为创建 namespace 和初始化键产生写入；这是首次初始化的预期行为。

## 28. On/Off 陈旧目标保护（离线编译，未烧录）

### 28.1 背景和决策

04:02 的工作区中有一个尚未提交的网关 freshness 草案：所有 MQTT 节点命令都要求最近 120 秒存在应用层 ZCL 上报。复审后认为该策略过宽，可能误伤 60 秒周期的实验电池 SED，以及未来更长上报周期的 sleepy 节点；同时 RF 命令路径已经有独立的节点表和发送失败后退避。

因此将策略收敛为两档：

- `rf_query_power / rf_set_auto / rf_set_power / rf_manual_power`：只检查 topic 中的短地址当前是否为 active child，不按应用层上报时间拦截；

- `zb_node_t` 中的时间字段从 `last_report_ms` 调整为 `last_seen_ms`，在 join/announce 和 ZCL report 时更新。

180 秒可覆盖当前 10 秒常电节点，也能容忍 60 秒电池 SED 连续三个周期未上报。该值仍是临时编译期常量，后续应随节点能力/上报周期配置演进，不应直接扩展成复杂的自动重启或离线判定机制。

- 本改动不写 NVS，不增加 Flash 磨损；
- 不改变 RF policy 的 durable desired mode/manual power；

- 被跳过的命令当前只在网关串口记录 warning，尚未向 MQTT 调用方发布 negative ACK。原因是命令状态协议需要前后端一起设计，不能在本轮静默改变接口；

## 45. CQ-1 FreeRTOS 生命周期加固与目标测试工程

### 45.1 背景

CQ-1 初版只提供消费者任务、业务队列和日志占位，复审发现启用后存在以下生命周期风险：

1. 消费者可能在队列句柄发布前运行并解引用空句柄；
2. 任务通知不能唤醒阻塞在普通业务队列接收中的任务；
3. 调用者任务通知不是 stop 事务私有信号，可能被其他通知干扰；
4. submit 释放状态锁后、调用 `xQueueSend()` 前可能与 stop 删除队列交叉；
5. stop 超时后若清除状态，会把无消费者的队列误报为正常运行。

这些问题在默认关闭且 `main.c` 未调用时不影响现网，但必须在后续启用前修复。

### 45.2 Queue Set 架构

当前 FreeRTOS 脚手架创建以下对象：

- `queue`：容量 8 的业务队列；
- `stop_event`：binary semaphore，仅用于停止；
- `queue_set`：容量 `RF_CQ_CAPACITY + 1`；
- `done`：每次 stop 事务私有的 binary semaphore；
- `rf-dispatch` 消费者任务。

业务队列与停止事件都加入同一个 Queue Set：

```text
xQueueCreateSet(RF_CQ_CAPACITY + 1)
xQueueAddToSet(queue, queue_set)
xQueueAddToSet(stop_event, queue_set)

消费者：
xQueueSelectFromSet(queue_set, portMAX_DELAY)
```

消费者阻塞时能被 `xSemaphoreGive(stop_event)` 唤醒；它只在 Queue Set 返回对应成员后，以零超时调用 `xQueueReceive()` 或 `xSemaphoreTake()`。

### 45.3 start/stop/submit 并发规则

- state mutex 使用 `xSemaphoreCreateMutexStatic()` 静态创建，不依赖堆内存；
- start 持有 state mutex 完成队列、Queue Set、任务创建和状态发布；
- submit 持有 state mutex 覆盖状态检查和非阻塞 `xQueueSend(..., 0)`；
- stop 持有 state mutex 标记 stopping、释放 stop_event 并等待完成；
- 消费者不获取 state mutex，因此 stop 等待期间不会阻止消费者响应 Queue Set；
- 消费者确认不再访问业务对象后，stop 才释放锁并删除队列、停止事件和 Queue Set。

这消除了“stop 删除队列时另一个 submit 正在调用队列”的交叉窗口。

### 45.4 消费者退出协议

消费者收到 stop_event 后退出事件循环：

```text
xSemaphoreGive(done)
vTaskDelete(NULL)
```

`done` 只表示消费者承诺不再访问业务队列、Queue Set 或 stop_event。之后消费者只负责自删除，不再访问任何可能被 stop 删除的对象。该协议比外部强制 `vTaskDelete()` 更安全。

### 45.5 超时 latched cleanup

如果等待 `done` 超时：

- 不删除队列、stop_event、Queue Set；
- 不把任务句柄和队列句柄清空；
- 保持 `s_stopping=true` 和 `s_rf_cq_done` 有效；
- start/submit/is_started 不会将其视为正常运行；
- 后续 `rf_cq_stop()` 可继续等待同一个 `done`，消费者晚到完成后再清理。

如果消费者始终无响应，对象暂时保留是有意的故障保持状态；正常成功路径没有任务或队列泄漏。

### 49.1 改动内容

三个函数只负责创建 `rf_dispatch_cmd_t`，不会启动队列、不会调用 Zigbee、不会写 NVS，也没有修改生产 `main.c`。

### 49.2 命令字段规则

| 构造函数 | source | command | desired_mode | desired_power_dbm | generation | backoff |
|---|---|---|---|---:|---:|---|
| user query | USER | QUERY | AUTO | 0 | ANY | 用户命令可绕过 backoff |
| user manual set | USER | SET | MANUAL | 用户指定功率 | ANY | 用户命令可绕过 backoff |
| user auto set | USER | SET | AUTO | 传入的当前功率 | ANY | 用户命令可绕过 backoff |

设计含义：

1. QUERY 不修改节点策略，`desired_mode=AUTO/power=0` 仅作为命令结构内的占位值，实际由 command=QUERY 决定；
2. MANUAL SET 必须携带目标功率，且目标功率必须属于支持表；
3. AUTO SET 用于把节点切回自动模式，功率字段使用调用时已知的当前功率，避免节点在模式切换瞬间跳到未知值；节点后续自动功率调整仍由后台控制；
4. 用户命令使用 `GENERATION_ANY`，因此不会被自身尚未完成的 generation 更新阻塞；但策略状态仍应在生产命令处理前 bump generation，使旧周期快照失效；
5. 用户命令允许绕过后台 backoff，但发送失败仍会更新失败计数和退避。

### 49.3 校验与 TTL

统一 base 构造函数会先校验：

- `id != 0`；
- `now_ms != 0`；
- request_id 必须为 16 字符小写 hex；
- 功率必须是支持值；
- 输出指针非空。

构造完成后再调用 `rf_cq_validate()`，保证生成对象满足现有队列校验。`deadline_ms = now_ms + 5000`，使用 tick wrap 兼容的有符号时间差。

TTL 取 5 秒的理由：消费者在没有回调阻塞时应很快取得命令；未来若队列积压，过期可以避免用户旧命令在几分钟后才控制节点。该值目前尚未接入现网，后续 CQ-2 接生产发送路径前还需结合客户端等待时间复核。

### 64.2 执行流程

1. MQTT 命令入口校验节点是否为当前 active child，并规范化 16 字节 request id；
2. MANUAL/AUTO 在 RF 状态锁内更新目标策略、清理旧 waiting、递增 policy generation，并持久化目标策略；
3. 新 intent 先写入 `s_rf_user_intent`，再提交到 CQ FIFO；
4. `rf-dispatch` 消费者取出命令后，在 RF 状态锁内重新生成纯计划、预留低序号并预登记 waiting；
5. 释放 RF 状态锁后获取 ZBOSS lock 并发送 APS 请求；
6. APS 返回后重新进入 RF 状态锁，只有 id/generation 仍匹配当前 intent 时，旧请求的结果才能修改当前状态；
7. REPORT 到达后按当前 waiting、序号、节点主动报告标记决定完成、重试或忽略。

### 64.3 旧事务保护

复审初次发现两个问题：

- 新 QUERY 在旧 waiting 尚未过期时也可能被 arm，旧 REPORT 可能把尚未发送的新 QUERY 标记完成；
- SET 完成逻辑未严格区分当前事务回复、旧私有回复和节点主动 REPORT。

已修复为：

- `rf_power_queued_query()` 在锁内先检查旧 waiting；只有 `rf_power_expire_waiting_if_due_locked(now)` 成功后才能 arm 新 QUERY；
- `rf_dispatch_after_report_state_t` 新增 `node_initiated_report`；
- 旧私有 REPORT 在 `matched_transaction=false` 且不是节点主动新报告时结果为 `NONE`；
- 节点主动 REPORT 只有在数值已经满足目标时才 `COMPLETE`，不满足时不触发立即重试；
- 当前事务匹配但 REPORT 显示未收敛时才 `RETRY`。

### 68.2 执行路径优先级

计划先校验 waiting/report submitting 的状态一致性，再按以下顺序判断：

1. 后台准入：
   - 60 秒 cadence；
   - RF backoff；
   - 节点 inactive；
   - 用户 intent active；
   - report waiting/submitting；
   - dispatch active；
   - background command active；
2. `NODE_STALE`：
   - `last_rx_ms=0` 或节点距上次收帧超过 120 秒；
   - 清理运行态 RF、waiting 和 background ownership；
   - 保留节点地址和 durable desired policy；
   - 标记 `policy_apply_pending=true`；
   - 本轮不发送；
3. waiting due：
   - 旧 waiting 满 90 秒后，先清旧 waiting 和旧 background ownership；
   - 产生周期 QUERY；
4. 正常 QUERY：
   - 当前功率 unknown 或距 confirmed 满 300 秒时产生周期 QUERY；
5. SET：
   - QUERY 计划返回 NO_SEND 后，根据 MANUAL/AUTO 目标产生周期 SET、清理 pending 或保持 idle。

当 stale 和 waiting due 同时成立时，stale 必胜；不会发包。waiting due 时如果 `report_submitting=true`，在途提交仍会阻止接管。

### 68.3 队列提交契约

`READY_QUERY` / `READY_SET` 只输出可进入单队列的 `rf_dispatch_cmd_t`，不直接触发 ZBOSS。调用方未来接入时必须：

1. 在同一 RF 锁内应用布尔状态并复制 command；
2. 释放锁后调用 `rf_cq_submit()`，不能直接发送；
3. 队列提交失败时重新进入 RF 锁：
   - 校验同一 command id 和 policy generation；
   - 只清理本次 background ownership；
   - 保留 `policy_apply_pending`；
4. 命令未成功入队前，不预留 Zigbee 序号，也不安装 report waiting。

成功 READY 的后台命令为 `RF_CQ_SOURCE_PERIODIC`，TTL 为 `RF_CQ_BACKGROUND_TTL_MS=2000 ms`，`ignore_backoff=false`，request_id 为空。

- `policy_generation != RF_CQ_GENERATION_ANY`。

- `NODE_STALE`；

## 69. CQ-3e：网关后台 RF 运行态适配层

### 69.1 修改范围

新增：

- `firmware/gateway/main/rf_background_runtime_adapter.h`
- `firmware/gateway/main/rf_background_runtime_adapter.c`
- `firmware/gateway/tests/test_rf_background_runtime_adapter.c`

修改：

- `firmware/gateway/main/CMakeLists.txt`：实验 ON 时编译运行态适配层；默认 OFF 不编译。

本阶段在不修改 `main.c` 的前提下，把网关现有 RF 全局状态映射到 CQ-3d 组合执行计划，并产出未来可直接提交到单队列的命令。模块仍为纯 C，不调用 FreeRTOS、ZBOSS、NVS 或网络。

### 69.2 适配动作

`rf_background_runtime_adapter_apply()`：

1. 校验运行态一致性，包括 waiting/submitting、active background command、mode/power 和策略版本；
2. 由 `tx_backoff_until_ms` 与当前时间推导 backoff active；
3. 调用 CQ-3d execution plan；
4. `REJECTED` 时返回不变状态；
5. `IDLE` / `POLICY_ALREADY_APPLIED` 只推进有效终态的 `last_eval`；
6. stale 时保留 `node_addr` 和 durable desired mode/manual power，重置当前功率、模式、confirmed、waiting 和 background ownership，并标记 policy pending；
7. READY QUERY/SET 时输出 `rf_dispatch_cmd_t`，并在 next state 中记录 active command id/generation。

普通周期 QUERY 不改变 `policy_apply_pending`：pending=false 时保持 false，pending=true 时也保持 true。

### 69.3 命令 ID 和回滚契约

`next_command_id` 是一次性、不可复用的输入，由未来集成层统一生成和管理；adapter 只消费，不自动推进。

队列提交失败后调用 `rf_background_runtime_rollback_command()`。该函数仅在以下条件全部满足时清理 background ownership：

- command source 为 `RF_CQ_SOURCE_PERIODIC`；
- background command active；
- active command id/generation 与输入命令匹配；
- 当前 policy generation 与命令匹配；
- 不存在 user intent、report waiting/submitting 或 dispatch active。

回滚不会清除 `policy_apply_pending`。旧 generation、非后台 source 或正在执行的事务都不能被误回滚。
