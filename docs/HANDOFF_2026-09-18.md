## 4. 解决的问题

### 4.1 旧节点固件的问题

21:34 左右，运行 `804eb4f` 的节点在链路异常后持续收到：

```text
Zigbee signal: 60
```

其中 60 是 `ESP_ZB_ZDO_DEVICE_UNAVAILABLE`。旧逻辑没有把它作为链路丢失处理，导致：

- 应用层仍认为 `s_zigbee_connected=true`；
- 节点持续采样并向协调器发送 APS 数据；
- APS failure 从两千多继续增长到三千多；
- repair 逻辑无法终止无效补发；
- 云端节点数据停在 21:34，但网关自身 MQTT 心跳仍正常。

这说明问题发生在节点对 Zigbee 链路状态的判断/恢复路径，而不是云端或 MQTT 主链路。

### 4.2 `05fc549` 的节点状态机修复

文件：

```text
C:/Users/HJB/Documents/iot-home/firmware/node_zigbee/main/main.c
```

主要变化：

1. 新增统一的 `schedule_network_steering(delay_ms)`：
   - 用 `s_network_steering_pending` 防止重复定时器堆积；
   - 调度前取消旧的 steering alarm。
2. 新增统一的 `zigbee_mark_connected(reason)`：
   - 设置在线状态；
   - 刷新短地址；
   - 清除 pending/forced 状态；
   - 取消尚未执行的 steering alarm。
3. 显式处理以下链路丢失信号：
   - `ESP_ZB_NWK_SIGNAL_NO_ACTIVE_LINKS_LEFT` = 24；
   - `ESP_ZB_ZDO_DEVICE_UNAVAILABLE` = 60。
4. 收到掉线信号后立即：
   - 设置 `s_zigbee_connected=false`；
   - 清空本地短地址缓存；
   - 关闭 APS report window；
   - 设置 `s_link_resteer_forced=true`；
   - 1 秒后强制重新 network steering。
5. `send_sensor_reports()` 在离线时直接跳过，不再盲目发新帧。
6. APS repair 等待期间发现链路已断开时立即停止 repair，等重新入网后再上报。
7. startup/rejoin 和 steering 失败分支读取 BDB commissioning status：
   - `NO_NETWORK` 等失败状态按 5 秒退避；
   - 若内部 rejoin 实际已成功且状态为 `ON_A_NETWORK`，接受为已连接，避免重复启动相互冲突的 steering。
8. 健康链路上周期性出现的 `ESP_ZB_NLME_STATUS_INDICATION` = 50 被显式忽略，不再刷屏或误判为掉线。
9. 删除了中间版本的 `IN_PROGRESS` busy-defer：定时器到点后直接启动 top-level commissioning；如果启动失败或收到 steering failed，再按 5 秒退避。

代码复核结论：独立 reviewer 未发现阻塞问题，未发现高置信度的状态机死锁、定时器重复泄漏、明显 Zigbee API 误用或恢复后继续无限补发问题。后续可考虑把多个 bool 收敛成单一连接状态枚举；如果将来到多个 Zigbee 对端通信，应解析 `DEVICE_UNAVAILABLE` 参数并区分不可用对端。

## 7. 仍未解决的网关侧问题

网关仍运行 `991bcb0-dirty`，其现有行为是：启动后先给 Zigbee 约 180 秒纯射频窗口，收满节点一轮温湿度/光照后才启动 Wi‑Fi/MQTT；Wi‑Fi/802.15.4 coex 已启用。

今天和前几天都观察到一个独立问题：

- 网关 Wi‑Fi/MQTT 和自身心跳仍正常；
- 但长时间运行后，已入网 ZED 的 rejoin 可能得不到响应；
- 节点可能短暂找不到父设备；
- 重启网关后通常能恢复。

本次节点修复只能在网关重新可响应后尽快自愈，不能修复网关 coordinator/parent 不响应 rejoin 的根因。下次应单独调查：

1. coordinator/parent 缓存或 neighbor/address resolution 状态；
2. Wi‑Fi/802.15.4 coex 在长时间运行后的调度影响；
3. permit join 只开放启动后 180 秒与已入网设备 rejoin 的关系；
4. 是否需要网关侧显式子设备超时、parent restart、网络状态日志或轻量恢复动作。

下次先静态分析网关代码并增加日志，再决定是否刷 COM6；不要把网关修复混入节点提交。

用户分享的 Arduino/Kconfig “Wi‑Fi 与 Zigbee 共存”文章不适用于本工程：当前项目是 ESP-IDF + esp-zigbee-lib，网关已配置 coex；不要按文章修改 Arduino Kconfig、示例分区表或应用框架。
