## 4. 三类问题归因

### 4.1 外部 PC 网卡/热点故障

- 00:20:06（uptime 9723.941 秒）网关首次出现 MQTT write completion stall/disconnected；
- 00:20:22 曾短暂恢复 15.7 秒；
- 00:21:52（uptime 9829.251 秒）再次断开，之后到采集结束再无 MQTT connected；
- 00:41:51（uptime 11028.681 秒）才首次出现 Wi-Fi beacon timeout；
- 从首次 Wi-Fi 链路断开到采集结束持续约 4.93 小时；
- 采集结束时仍无重新获取 IP。

判断：MQTT 异常最初约 21 分 45 秒内未见 Wi-Fi 链路断开，说明热点可能仍有关联但上游/MQTT 可达性异常；之后 AP 本身不可用。该段主要是外部网络事件，不应简单归为固件故障。

### 4.2 Zigbee 父链路稳定性问题

- 首次 `Rejoin failure` 在 22:43:32（uptime 3929.950 秒），比 MQTT 首次异常早约 5794 秒；
- `Rejoin failure` 共 990 行，聚类为 7 组；
- 正式 link lost 共 26 次；
- 最长一次为 00:23:02–00:42:47，持续 1185.33 秒（19 分 45 秒）；
- 长中断期间节点任务按设计等待网络，常规 DATA 暂停；恢复后业务继续；
- 后续 22 次 link lost 多数 1–6 秒恢复，但发生频率仍说明父链路裕度或协议状态不稳定。

### 4.3 I2C/OLED 独立总线问题

- clear bus error：29 次；
- OLED refresh failed：6 次；
- 每次均通过本地 I2C/SSD1306 reset 恢复；
- 事件主要集中在 21:38–00:20，另有一次 03:06；
- 与 PC 网卡掉线无直接时间对应，也未长期阻断 Zigbee/MQTT 业务。

优先硬件整改：固定并缩短 SDA/SCL、增加 4.7 kΩ 上拉、OLED VCC 就近增加 100 nF 去耦。Flash 剩余约 54 KB，整改前不盲目叠加固件逻辑。

## 6. 决策与下一步

1. 保持当前默认 OFF 固件和当前检查点，不覆盖当前固件；
2. 暂缓原计划的 Zigbee 应用事件队列/事件处理拆分（P2-1～P2-4）；
3. 先完成 OLED 接线/上拉/去耦硬件整改；
4. 节点改用确认可靠的 USB 数据线；
5. 在 Windows 热点和外网持续稳定条件下安排受控 8 小时复测；
6. 若受控复测仍复现父链路异常，再深入排查 ZBOSS polling/rejoin、child aging、coexistence 和供电，不先叠加新功能；
7. 若需要确认当前实时状态，先征得用户同意后再打开串口，因为打开 COM5/COM6 可能触发复位。
