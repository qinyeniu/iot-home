## 3. 关键发现：旧行为 = "迟到入库" + "永久丢失"

2026-09-22 08:14 曾精确对齐：网关日志显示 08:10–08:13 共发布 **19 帧**，
当时云端只查询到 **11 帧**。约 50 分钟后复查同一时间窗口：

- 窗口内样本从 11 增加到 **14**——有 3 帧在后续才入库，
  且保留**原始设备时间戳**（迟到的是"写库动作"，不是补采）；
- 仍有 **5 帧永久缺失**（14/19，该小窗口丢失率 26%）。

这解释了早期观察到的"同帧指标 created_at 相差数秒"：
旧后端在低配 VPS 上处理积压，消息以原始 ts 延迟落库；
积压超出 broker/协议栈缓冲能力的部分则永久消失。

## 4. 根因与修复状态

根因（详见 `docs/HANDOFF_2026-09-22.md` 第 11 节）：

1. 后端以 QoS0 订阅，且收包与慢数据库写入耦合，积压时无重传；
2. 节点/网关侧无责任（节点 APS 成功率近 100%，网关 200 秒观测零丢失）。

已完成的修复（本地）：QoS1 订阅、收发解耦、批量写库、持久会话；
本地 broker 端到端两场景零丢失（60 帧慢处理、30 帧断连重启）。

**线上仍运行旧版本，本报告中的丢帧行为仍在持续；
部署新后端后应用同样方法复测，预期送达率接近 100%。**
