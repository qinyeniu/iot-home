## 3. 本轮发现的问题

上一版固定 `-10 dBm` 固件在近距离桌面完成过 1 小时稳定性观察；后续未提交的 ATPC 初版存在误调功率风险，实测表现如下：

1. 网关在 APS callback 稍后调用 `esp_ieee802154_get_recent_rssi()`，读到约 `-90` 到 `-101 dBm` 的陈旧/共存值；当时 Zigbee 帧实际成功。
2. 初版又把该 RSSI 或通用 LQI 阈值当作弱链路，节点仍在成功上报时被连续提高到 `+14 dBm`、`+18 dBm`。
3. 同一短地址节点复位后，网关没有丢弃上一轮功率状态，可能把旧进程的高功率错误套到新进程。
4. REPORT 等待超时使用“最近收包时间”判断；由于普通遥测持续到达，丢失私有 REPORT 时可能一直等待。
5. 启动阶段在 `esp_zb_start()` 之前读取 TX power，可能显示默认 `+20 dBm`，不能据此认定设置失败。

## 13. 2026-09-23 严格事务边界最终加固

### 13.1 本轮解决的问题

上一版运行时功率控制仍有几个严格事务边界：

1. 节点主动 REPORT 与网关命令响应需要进一步隔离，主动上报不能携带本次命令事务号；
2. 90 秒超时只在 60 秒周期控制任务中处理，周期任务运行前的迟到精确 REPORT 仍可能确认旧事务；
3. 链路陈旧超过 120 秒时，旧逻辑可能解除 durable policy 的后续应用状态，导致恢复后期望模式与节点实际状态长期不一致；
4. 节点本来已经处于用户要求的 `manual/power` 且本次 SET 本地发送失败时，下一轮只清理 pending，不发布 confirmed；
5. 幂等确认路径还存在一个很短的 TOCTOU 抢占窗口。

最终修复：

- 网关命令响应用低序号 `1..127`；节点主动 REPORT 用高序号 `0x80..0xFF`；
- 只有加密 v2 REPORT 的序号、功率、模式全部匹配，并且 `expected_user=true`，才发布携带本次 `request_id` 的 confirmed；
- v1 REPORT 不能证明 manual/auto 模式；
- REPORT 到达时实时判断 deadline，超时后的迟到回包不能确认旧事务；
- 陈旧断连只终止用户请求，不删除 NVS 中的期望模式和手动功率；恢复后自动 QUERY/SET 对账；
- 幂等场景在最终确认前于锁内二次校验完整事务上下文；若期间被新命令替换，则旧事务不清理、不确认。

若此前明文 MQTT 已长期运行，完成网络保护迁移后建议轮换后端和网关 MQTT 密码。

### 16.4 非阻塞待办

- 准备 TLS 证书、Mosquitto TLS listener、后端/固件 TLS 连接；
- MySQL root 密码当前可能出现在 Compose healthcheck 进程参数中，后续改为专用健康检查账号或配置文件；
- 继续定位节点 `vPortExitCritical` 断言；
- 整夜采集结束后使用分析器生成最终报告。
