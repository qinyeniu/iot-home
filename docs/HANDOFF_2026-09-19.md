## 4. 这次改动解决什么

现网长期观察到的问题是：

- 网关 Wi‑Fi/MQTT 心跳仍正常；
- 但偶发长时间运行后，已入网 sleepy end device 的 rejoin 可能得不到及时响应；
- 重启网关后通常恢复。

昨天的节点修复 `05fc549` 已能在网关恢复响应后自动重新 steering，但它不能证明或修复网关侧根因。今天的 `799c5d0` 是网关侧**低风险静态改进 + 诊断增强**，用于对齐官方主循环并捕获下一次异常前后的 Zigbee 信号时序。

**注意：目前不能宣称已经根治 rejoin 问题。**主循环替换是合理的官方对齐改进，但仍需刷入后做受控启动验收和后续长时间观察。

## 5. `799c5d0` 具体变化

文件：

```text
C:/Users/HJB/Documents/iot-home/firmware/gateway/main/main.c
```

### 5.1 使用官方专用 Zigbee 主循环

旧逻辑在 Zigbee 任务中每 100 ms 手动轮询一次已废弃接口：

```c
while (1) {
    esp_zb_main_loop_iteration();
    vTaskDelay(pdMS_TO_TICKS(100));
}
```

新逻辑对齐 ESP-Zigbee 1.6.0 头文件和官方示例：

```c
ESP_ERROR_CHECK(esp_zb_start(false));
esp_zb_stack_main_loop();
vTaskDelete(NULL);
```

同时：

- `esp_zb_cfg_t` 改为指定初始化器，确保 union 和未显式设置字段清零；
- `esp_zb_start(false)` 的返回值纳入 `ESP_ERROR_CHECK`；
- 不改变 coordinator 角色、channel mask、PAN、NVRAM、endpoint 或 cluster 注册。

### 5.2 新增 rejoin/permit/NLME 诊断

普通任务中新增日志处理以下信号：

- `ESP_ZB_NWK_SIGNAL_PERMIT_JOIN_STATUS`；
- `ESP_ZB_SE_SIGNAL_REJOIN`；
- `ESP_ZB_SE_SIGNAL_CHILD_REJOIN`；
- `ESP_ZB_BDB_SIGNAL_TC_REJOIN_DONE`；
- `ESP_ZB_NWK_SIGNAL_NO_ACTIVE_LINKS_LEFT`；
- `ESP_ZB_ZDO_DEVICE_UNAVAILABLE`；
- `ESP_ZB_NLME_STATUS_INDICATION`。

permit duration 的日志规则：

- `0`：joining closed，同时提示 secure rejoin 仍可使用既有凭据；
- `0xff`：保守打印 `duration=0xff`，不写死成永久；
- 其他值：按秒打印。

新增日志用于判断：

- 启动/组网后 permit join 是否真的打开和关闭；
- 节点异常时是否发起 secure/child/Trust Center rejoin；
- 网关是否看到 no active links 或 device unavailable；
- NLME status 的真实错误码、短地址和 unknown command id 是什么。

### 5.3 ZBOSS callback 保持非阻塞

新增信号不在 ZBOSS callback 中直接打日志，而是复制为小事件后投递给普通任务，避免再次触发 restricted/ISR-like callback 中 VFS logging abort 风险。

投递使用：

```text
xQueueSend(..., 0)
xQueueSendFromISR(..., &higher_woken)
portYIELD_FROM_ISR(...)
```

callback 中没有新增：

- 日志/VFS；
- NVS；
- MQTT；
- 动态内存；
- 延时或阻塞等待。

### 5.4 业务事件和诊断事件队列隔离

现在有两条队列：

```text
s_zb_app_q     length 32  -> join/report/leave 业务事件
s_zb_signal_q  length 16  -> permit/rejoin/NLME 等诊断事件
```

普通任务通过一个 FreeRTOS queue set 等待两条队列，并严格做到：

```text
select 到哪个队列，就只从该队列 receive 一条事件
```

这样即使异常网络触发诊断风暴，也只会丢弃诊断事件，不能占满 join/report/leave 的业务队列。

丢弃统计拆成：

```text
business event queue drops: task / isr-like
diagnostic event queue drops: task / isr-like
```

每类最多 60 秒打印一次。

### 5.5 NLME payload 的安全处理

应用代码不能直接包含 `zboss_api_zdo.h`：直接 include 会因为内部头文件依赖顺序产生大量类型编译错误。

当前版本在 `main.c` 内定义仅用于读取 payload 的最小 ABI 兼容结构：

```c
typedef struct __attribute__((packed)) {
    uint8_t status;
    uint8_t network_addr_le[2];
    uint8_t unknown_command_id;
} gw_zb_nlme_status_indication_t;
```

短地址按两个字节手动小端拼装，避免 packed 结构里的非对齐 16 位访问。

同时加入编译期断言，锁定当前 esp-zboss-lib 1.6.0 的布局：

```text
size == 4
status offset == 0
network address offset == 1
unknown command offset == 3
wrapper size == 4
```

健康网络中会周期性出现 `NLME status=0`，该状态直接忽略；非 0 NLME 指示现在做**全局限流**：无论状态码是否交替，每分钟最多保留一条。

## 10. 串口监视器清理方式

如果监视器无法正常退出，只能按完整命令行和目标端口精确结束，禁止只按 `python.exe` 批量杀进程。

COM6：

```powershell
Get-CimInstance Win32_Process -Filter "Name = 'python.exe'" |
  Where-Object { $_.CommandLine -match 'idf_monitor|esp_idf_monitor' -and $_.CommandLine -match 'COM6' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

不要用 `read_flash ... NUL` 长时间占用串口做测试。
