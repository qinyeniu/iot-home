# 电池节点低功耗改造方案

更新时间：2026-09-24  
状态：方案第一版；暂不修改当前已实测的组合节点固件  
目标：后续新增独立电池供电传感器节点，而不是把带继电器的节点强行电池化

## 1. 核心结论

当前 `firmware/node_zigbee` 是“传感器 + 继电器 + 本地按钮”组合节点，主要按常供电和快速响应设计，不适合直接作为电池节点：

1. 继电器吸合需要持续电流；
2. 继电器低电平触发，安全设计依赖常供电和 GPIO 状态；
3. 当前传感器任务持续运行，调试周期为 10 秒；
4. 当前固件没有启用 Power Management / FreeRTOS tickless；
5. 立即开关命令与深度睡眠天然冲突。

因此建议：

- **执行器/继电器节点继续常供电；**
- **新增独立的电池传感器节点；**
- 电池节点优先上报环境数据，不承诺立即执行开关；
- 先做实验工程和电流实测，再修改主工程。

## 2. 目标设备类型

### 2.1 电池环境传感器

传感器：

- AHT20：温度/湿度；
- BH1750：光照；
- 可选：电池电压、电池电量、唤醒次数、复位原因。

默认上报周期：

- 调试：60 秒；
- 日常：5 分钟；
- 低功耗：15–20 分钟。

目标：

- 睡眠电流先用仪表确认，阶段目标 `< 20 µA`；
- 常规唤醒和上报时间尽量短；
- 电池续航以实测为准，不只用理论值。

### 2.2 电池开关/门窗传感器

后续可做：

- GPIO 中断唤醒；
- 磁簧/按钮状态变化立即上报；
- 定时心跳；
- 绝大多数时间睡眠。

### 2.3 继电器执行器

不建议普通继电器线圈长期电池供电。可选硬件：

- 常供电继电器；
- 脉冲继电器 / 磁保持继电器；
- 单独低功耗执行器。

## 3. 两种低功耗技术路线

## 3.1 Zigbee Sleepy End Device（推荐先做）

特点：

- MCU 仍保持 RAM 和任务；
- 启用 ESP-IDF Power Management 和 FreeRTOS tickless；
- Zigbee 栈在空闲时进入睡眠；
- 节点周期性向父节点 poll，查看是否有缓存命令；
- 通过 Zigbee 标准 End Device Timeout 告知父节点自己可离线多久。

当前 ZBOSS 提供 `zb_esp_sleep.h`，其中相关能力依赖：

```text
CONFIG_PM_ENABLE
CONFIG_FREERTOS_USE_TICKLESS_IDLE
```

优点：

- 网络上下文保活；
- 比每次重新入网更可靠；
- 可以支持有限的下行命令；
- 适合先验证 Zigbee SED。

风险：

- 睡眠电流可能高于 deep sleep；
- 外设和板级漏电必须逐个确认；
- 若 poll 周期太短，平均电流会上升。

## 3.2 Deep Sleep Duty-cycle（最终省电路线）

特点：

- 每次唤醒后执行采样、上报、有限 poll；
- 完成后进入 deep sleep；
- 下一次周期唤醒重新启动应用；
- Zigbee 网络信息依赖 Zigbee NVRAM 和 secure rejoin。

优点：

- 睡眠电流最低；
- 软件状态简单；
- 适合 5–20 分钟一次的环境监测。

风险：

- 每次唤醒都有重新启动和链路恢复成本；
- 若 rejoin 不稳定，反而更耗电；
- 下行命令不能即时到达；
- 需要保留 Zigbee NVRAM，不能擦除。

建议：先做 SED，确认通信和电流；再做 deep sleep 实验固件。

## 4. 推荐工作流程

### 4.1 SED 模式

```text
唤醒/空闲
  ↓
Zigbee 栈保活
  ↓
按周期读取传感器
  ↓
发送加密 ZCL report
  ↓
等待 APS confirm（有超时）
  ↓
向父节点 poll 是否有下行命令
  ↓
无命令则继续 Zigbee sleep
```

### 4.2 Deep Sleep 模式

```text
定时唤醒/按键唤醒
  ↓
启动应用并初始化必要外设
  ↓
读取电池电压和传感器
  ↓
通过已保存 Zigbee 网络状态发送 report
  ↓
有限等待 APS confirm
  ↓
短 poll 下行命令
  ↓
设置下次唤醒时间
  ↓
进入 deep sleep
```

发送失败时不做无限重试：

- 本次最多少量重试；
- 失败计数随下次上报；
- 下次唤醒重新读当前值；
- 不保存大量历史数据，不增加 Flash 磨损。

## 5. 硬件低功耗要点

### 5.1 传感器电源

需要确认：

- AHT20 sleep 电流；
- BH1750 power-down 电流；
- I2C 上拉电阻是否在睡眠时漏电；
- GPIO 状态是否通过传感器形成电流路径；
- 必要时增加负载开关，仅采样时给传感器供电。

I2C 上拉建议使用较大阻值，但要兼顾通信可靠性。

### 5.2 板级漏电

需要逐一排查：

- USB-UART 芯片；
- 板上 LED；
- 按键分压/上拉；
- OLED/显示屏；
- 继电器模块；
- 稳压芯片静态电流；
- 未使用 GPIO 默认状态；
- 调试器连接造成的电流。

电池节点不应焊接常亮指示灯。

### 5.3 继电器节点

当前组合节点若继电器 ON，线圈电流可能远高于 MCU 自身电流，不能用于电池寿命评估。

电池节点第一版建议完全不带普通继电器。

## 6. 电池与电源方案

### 6.1 18650（第一阶段推荐）

优点：

- 容量大；
- 可重复充电；
- 电压范围适合 C6；
- 容易做反复唤醒测试。

需要：

- 合适 LDO 或 DC-DC；
- 充电保护；
- 电池保护板；
- 低静态电流电源芯片。

### 6.2 2×AA 碱性

标称 3.0V，但放电末期可能低于 C6 和外设稳定工作电压。

直接供电风险较大，需要：

- 高效低静态 buck-boost；
- 或 3×AA 配合 LDO；
- 实际低压曲线测试。

### 6.3 Li-SOCl2 AA

标称 3.6V，容量高，但需要考虑：

- 脉冲能力；
- 瞬时大电流电压跌落；
- 并联脉冲电容；
- 电池选型和安全。

适合后续成熟低功耗节点，不建议第一版直接使用。

## 7. 功耗预算方法

平均电流：

```text
平均电流 = 睡眠电流 + 各唤醒任务电流 × 持续时间 / 上报周期
```

示例（仅说明公式，不作为实测值）：

- 睡眠：15 µA；
- 每次唤醒平均等效：50 mA × 0.3 秒；
- 周期：60 秒。

唤醒平均电流约：

```text
50 mA × 0.3 / 60 = 0.25 mA = 250 µA
```

总平均约 265 µA；2500 mAh 电池粗略可运行：

```text
2500 mAh / 0.265 mA ≈ 9434 小时 ≈ 393 天
```

若周期延长到 5 分钟，唤醒平均约 50 µA，总平均约 65 µA，理论续航会显著增加。

以上必须通过功率分析仪/万用表和真实 Zigbee 网络修正。高功率重试、rejoin、Wi‑Fi 调试连接都可能让结果明显变差。

## 8. RF 功率与电池策略

电池节点应继续遵守安全启动：

- 上电从 `-10 dBm`；
- 不恢复曾经保存的高功率；
- 只有真实失败达到阈值才升档；
- 设置重试上限。

电池场景与常供电不同：

- 不应为了追求一次发送成功长时间重试；
- 长失败可推迟到下次唤醒；
- 可增加失败计数和最近失败原因；
- AUTO 升功率后，应在下一次成功且链路稳定时谨慎降回低档。

## 9. 下行命令的语义变化

当前 API 对开关命令有确认窗口，超时后标记 timeout。对于深睡节点，命令可能要等下一次唤醒才执行，这需要后续产品逻辑支持。

未来状态可能是：

```text
pending（云端待发）
  ↓
deferred（网关等待节点唤醒）
  ↓
sent（节点本次 poll/report 时发送）
  ↓
acknowledged（节点回报状态）
```

这涉及前后端状态、命令超时和 Grafana/API 展示，不能在今晚贸然修改。

当前建议：

- 电池传感器第一版只读，不承担继电器控制；
- 后续电池门窗传感器只上报事件，不要求云端立即反向控制；
- 等节点状态机稳定后，再设计 deferred command。

## 10. 新增电池指标

后端通用 metrics 表可以直接接受数值字段，无需立即改表。

建议后续固件在 `data` 中加入：

| 指标 | 含义 |
|---|---|
| `battery_voltage` | 电池电压，V |
| `battery_level` | 估算电量百分比 |
| `wake_count` | 累计唤醒次数 |
| `sleep_interval_s` | 本次目标睡眠/上报周期 |
| `tx_fail_count` | 累计发送失败次数 |
| `reset_count` | 复位次数 |

这些指标应低频写入，避免每次变化都写 NVS。累计计数可在周期重启时保存在 RTC 内存或低频 NVS；第一版可以只输出本次启动计数。

## 11. 实施阶段

### 阶段 1：实验工程

- 新增独立 `firmware/node_battery` 或等价实验目录；
- 不改变现有 `firmware/node_zigbee`；
- 复用 I2C 传感器和 ZCL report 代码；
- 去掉继电器和本地持续按钮任务。

### 阶段 2：SED 配置

- 启用 PM 和 tickless；
- 接入 `zb_esp_sleep_init()` 等能力；
- 配置合理的 End Device Timeout；
- 使用 60 秒周期验证。

### 阶段 3：电流实测

记录：

- 开发板连接/断开 USB-UART 时电流；
- 睡眠电流；
- 采样电流；
- Zigbee 发送电流；
- APS fail/rejoin 电流；
- 不同上报周期电流。

### 阶段 4：Deep Sleep 版本

- 周期 deep sleep；
- 保留 Zigbee NVRAM；
- 唤醒后 secure rejoin/report；
- 强制断电和低压测试。

### 阶段 5：前后端产品语义

- deferred command；
- 电池指标和告警；
- Grafana 电池面板；
- 设备能力模型中标注 battery/sensor/sleepy。

### 阶段 6：硬件版本

- PCB 去除漏电元件；
- 低静态电源；
- 电池保护；
- 外壳和电池仓；
- 产线配网/标签。

## 12. 验收标准

### SED 版本

- 可稳定加入/重新加入；
- 遥测可持续到达；
- 平均电流实测达到预期；
- 无异常高功率；
- 不出现断言重启；
- 父节点重启后能恢复。

### Deep Sleep 版本

- 每次定时唤醒；
- 上报成功率可接受；
- Zigbee NVRAM 不丢失；
- 电池电压下降时行为明确；
- Flash 不被频繁写入；
- 长周期下续航满足实测目标。

## 13. 今晚不做事项

- 不直接改当前已验证的组合节点为低功耗；
- 不擦 Zigbee NVRAM；
- 不启用 eFuse/Flash encryption；
- 不做远程部署；
- 不在未测量电流前承诺续航；
- 不贸然修改前后端命令超时语义。
